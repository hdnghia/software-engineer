SOLID, made visual

Five design rules that keep code easy to change. For each one: a real-life analogy, the broken design, the fixed design, and a button to feel the difference.

S · Single Responsibility

One class, one reason to change

A class should do one job. If two different people could ask you to change it, it does too much.
🍳
Restaurant. If one person cooks, takes payment and cleans, a new tax law forces you to retrain the cook. With separate roles, only the cashier changes.
class Invoice {
  calculateTotal() {...}   // business
  saveToDatabase() {...}   // persistence
  printPdf() {...}         // presentation
}
class Invoice        { calculateTotal() }
class InvoiceRepo    { save(invoice) }
class InvoicePrinter { toPdf(invoice) }

O · Open / Closed

Add new behavior without editing old code

Open for extension, closed for modification.
🔌
Power strip. To plug in a new device you don't rewire the wall. You just plug it in. Your code should accept new "devices" the same way.
function pay(type, amount) {
  if (type === "card")   {...}
  else if (type === "paypal") {...}
  // new method? edit this function again!
}
interface Payment { pay(amount) }
class Card   implements Payment {...}
class PayPal implements Payment {...}
class Crypto implements Payment {...}  // new file only

function checkout(p: Payment, amt) { p.pay(amt) }

Smell: a growing if/else or switch on a "type". Replace it with polymorphism.
L · Liskov Substitution

A child must work wherever its parent works

If code works with Bird, it must also work with any subclass of Bird, without surprises.
🐧
Penguin. Is a penguin a bird? Yes. Can it fly? No. If Bird promises fly(), a penguin breaks that promise. The model is wrong, not the penguin.
class Bird { fly() {...} }
class Sparrow extends Bird {...}
class Penguin extends Bird {
  fly() { throw Error("can't fly") }
}
class Bird { eat() {...} }
class FlyingBird extends Bird { fly() {...} }
class Sparrow extends FlyingBird {}
class Penguin extends Bird { swim() {...} }

Smell: a subclass that throws "not supported", returns nothing, or needs an instanceof check. Fix the hierarchy, not the caller.
I · Interface Segregation

Don't force clients to depend on what they don't use

Prefer several small, focused interfaces over one big one.
🖨️
Multifunction printer. A cheap printer that must implement scan() and fax() just to satisfy one giant interface ends up with fake, broken methods.
interface Machine { print(); scan(); fax(); }

class BasicPrinter implements Machine {
  print() {...}
  scan() { throw "unsupported" }
  fax()  { throw "unsupported" }
}
interface Printer { print() }
interface Scanner { scan() }
interface Fax     { fax() }

class BasicPrinter implements Printer {...}
class OfficeAllInOne implements Printer, Scanner, Fax {...}

Smell: empty methods or throw NotSupported inside an implementation. Split the interface by client need.
D · Dependency Inversion

Depend on abstractions, not concrete details

High-level code should not know low-level details. Both should depend on an interface.
💡
Wall switch. The switch doesn't care if it controls a bulb, a fan or a heater. It only knows "on/off". Welding a switch to one bulb means rewiring to change it.
class Switch {
  bulb = new LightBulb()  // hard-wired
  press() { this.bulb.turnOn() }
}
interface Switchable { turnOn(); turnOff() }
class LightBulb implements Switchable {...}
class Fan       implements Switchable {...}

class Switch {
  constructor(private d: Switchable) {}
  press() { this.d.turnOn() }
}

Cheat sheet

LetterQuestion to askRed flag
SDoes this class have more than one reason to change?Name contains "and"; huge class
OCan I add a feature without editing existing code?Long if/else or switch on type
LCan a child replace its parent safely?Overrides that throw or do nothing
IDoes the client use every method it must implement?Empty / "unsupported" methods
DDoes my logic depend on interfaces, not concrete classes?new inside business logic
Remember them as one idea: keep pieces small, swappable and honest, so a change in one place doesn't break ten others. They are guidelines, not laws. Don't over-engineer tiny programs.
