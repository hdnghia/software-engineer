Lesson 1 · Foundations

What actually happens on read()

I/O moves bytes between memory and the outside world: disks, networks, terminals, GPUs. Devices are 100× to 1,000,000× slower than the CPU, so nearly every technique in this atlas falls into one of three ideas.

1 · Don't wait

Overlap waiting with work

Interrupts, non-blocking sockets, event loops, async I/O, goroutines.

2 · Batch

Pay fixed costs fewer times

Buffers, read-ahead, write-back, io_uring rings, request merging.

3 · Don't copy

Let hardware move the bytes

DMA, page cache, mmap, sendfile, splice.

Lesson 3 · Hardware

How the CPU talks to a device

A device controller exposes registers (status, command, data). The CPU reaches them through port-mapped I/O (x86 in/out instructions) or, more commonly today, memory-mapped I/O (MMIO), where device registers appear at physical addresses. The real question is how the CPU learns that the device is done.

Polling (programmed I/O)

CPU loops reading the status register. Lowest latency, but it burns 100% of a core while waiting.

Interrupt-driven

Device raises an interrupt when ready. CPU does other work but still copies each word itself.

DMA

CPU programs a DMA engine with an address and length. The device writes straight into RAM and raises one interrupt at the end.

Polling is making a comeback at the high end. NVMe io_poll, DPDK and SPDK spin on purpose because a µs-scale device finishes faster than an interrupt plus context switch would take. Linux NAPI switches between interrupts and polling depending on load.
Lesson 4 · Operating system

System calls: crossing into the kernel

User programs cannot touch devices directly. They ask the kernel through a system call: arguments go into registers, a syscall instruction switches the CPU to kernel mode, the kernel does the work, then returns with sysret.

Mode switch ≠ context switch

A syscall is a mode switch (~100 ns to 1 µs with Spectre/Meltdown mitigations). If the call blocks, the scheduler runs another thread. That context switch costs a few µs and pollutes the CPU caches.

File descriptors

Everything is an fd: files, sockets, pipes, eventfd, timerfd. An fd is an index into the process's fd table, which points to a kernel struct file. That shared shape is what lets one epoll watch all of them.

Blocking is a kernel decision

When data isn't ready, the kernel puts the thread on a wait queue and marks it sleeping. The device interrupt later wakes it. With O_NONBLOCK, the kernel returns EAGAIN instead.

// The entire I/O universe on Unix funnels through a handful of calls
fd = open("data.log", O_RDONLY);          // get a descriptor
n  = read(fd, buf, 4096);               // may block until data arrives
n  = write(sock, buf, n);              // may block if the socket send buffer is full
fsync(fd);                              // block until data is on stable storage
close(fd);

Tip: run strace -c ./your_program to count syscalls by type, and strace -T to see time spent in each one. It is often the fastest way to find an I/O bottleneck.

Lesson 5 · Operating system

Buffering: fewer, bigger syscalls

Every syscall has a fixed cost. Writing 1 byte at a time to a file means one syscall per byte. A user-space buffer (bufio, stdio, BufferedWriter) gathers small writes and flushes them in large chunks.

Write 1 MiB in small pieces

Model: ~0.5 µs per syscall plus ~20 GB/s memcpy. Real numbers vary, but the shape does not.

// Go: wrap the file, then always Flush (or data stays in user space!)
f, _ := os.Create("out.txt")
w := bufio.NewWriterSize(f, 64*1024)
for _, line := range lines { w.WriteString(line) }
w.Flush()   // one write() per 64 KiB instead of one per line
f.Sync()    // fsync: see Lesson 12
Trade-off: buffering adds latency and risk. Data in the buffer is invisible to readers and lost if the process crashes. Interactive output such as a terminal is line-buffered for this reason, and network protocols flush at message boundaries.
Lesson 6 · Operating system

Zero-copy: serving a file without touching it

A static file server naively does read(file) then write(socket). The bytes pass through user space for no reason. Zero-copy techniques keep them inside the kernel or let DMA do the work.

Follow the bytes

    Used by Nginx (sendfile on;), Kafka (consumers are served with sendfile, which is a big part of why Kafka is fast), and Java's FileChannel.transferTo(). splice() does the same between any fd and a pipe. With kTLS, the kernel can encrypt TLS traffic inside a sendfile path.

    Lesson 7 · I/O models

    The five I/O models (Stevens, UNP)

    Every input operation has two phases. Phase 1: wait for the data to be ready (packet arrives, disk finishes). Phase 2: copy it from the kernel to your buffer. The models differ only in what your thread does during each phase.

    Multiplexing: select vs poll vs epoll

    One thread, thousands of sockets. The question is how the kernel tells you which sockets are ready. select and poll rescan every fd on every call. epoll keeps a persistent interest list and a ready list in the kernel.

    Level-triggered vs edge-triggered

    Level-triggered (LT) reports "this fd is readable" as long as data remains. Edge-triggered (ET) reports only when new data arrives. With ET, you must read until EAGAIN, or leftover bytes sit there with no further wake-up.

    Try: arrive → wait → read → wait. LT wakes you again because 1 KB is still there. ET stays silent and the 1 KB is stranded.

    Lesson 9 · I/O models

    io_uring: true async I/O via shared rings

    Since Linux 5.1. The app and kernel share two ring buffers in memory. The app writes requests to the Submission Queue, and the kernel posts results to the Completion Queue. One io_uring_enter() can submit many operations, and in SQPOLL mode a kernel thread polls the SQ so you need no syscalls at all.

    Drive the rings
    Submission Queue (app writes tail, kernel reads head)
    In flight inside kernel / device
    Completion Queue (kernel writes tail, app reads head)
    // liburing, minimal read
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buf, 4096, 0);
io_uring_submit(&ring);                  // one syscall for N SQEs
io_uring_wait_cqe(&ring, &cqe);          // cqe->res = bytes read or -errno
io_uring_cqe_seen(&ring, cqe);
    Unlike epoll, io_uring works for regular files. epoll treats files as "always ready" and reads still block on disk, which is why Node.js and Go push file I/O onto thread pools. It also supports linked ops, fixed buffers and registered files.
    Lesson 10 · Architectures

    How servers juggle 100,000 connections

    The "C10K problem" (Dan Kegel, 1999): one thread per connection doesn't scale because threads cost memory and context switches. Each answer below is a way of mapping many I/O waits onto few CPUs.

    Memory cost of idle connections

    Assumes ~1 MiB per OS thread stack plus kernel structures, ~4 KiB per goroutine, ~2 KiB of state per event-loop connection. Socket buffers are excluded because every model pays those.

    Thread per connection

    Simple blocking code. Fine up to a few thousand connections, then it hits memory limits and scheduler thrash. Apache prefork, classic JDBC, Java BIO.

    Reactor (event loop)

    epoll tells you when a socket is ready, then non-blocking handlers do the I/O. One loop per core. Never block the loop! Nginx, Redis, Node.js, Netty.

    Proactor

    You start the operation and get called when it's done, with data already in your buffer. Windows IOCP, io_uring, Boost.Asio.

    Green threads

    You write blocking-style code, and the runtime parks the cheap thread and uses epoll underneath. Go goroutines + netpoller, Java 21 virtual threads, Erlang.

    Reactor loop in one picture

    for {
    events := epoll_wait(epfd, -1)            // the ONLY place we block
    for _, ev := range events {
        switch {
        case ev.fd == listener: conn := accept(); epoll_ctl(ADD, conn, EPOLLIN)
        case ev.readable:        n := read(ev.fd, buf)   // won't block: data is there
                                 handle(buf[:n])      // must be fast; CPU work → worker pool
        case ev.writable:        flushPending(ev.fd)
        }
    }

    Lesson 11 · Storage

    Storage devices & disk scheduling

    An HDD has a moving arm. Each random access costs a seek (~4–10 ms) plus rotational latency (~4 ms at 7200 rpm). Disk schedulers reorder requests to minimise arm travel. SSDs have no arm, so Linux uses none or mq-deadline for NVMe.

    This is why databases use append-only logs (WAL, LSM-trees in RocksDB and Cassandra): they turn random writes into sequential ones. Kafka's design rests on the same idea.
    Lesson 12 · Storage

    write() returned. Is my data safe?

    Usually not yet. write() only copies bytes into the kernel page cache and marks the pages dirty. A writeback thread flushes them to disk later (default ~5–30 s). Reads hit the page cache too, and read-ahead prefetches sequential data.

    Bypasses the page cache, so the app manages its own cache (databases do this). It needs aligned buffers and still needs fsync for the device cache.

    fdatasync vs fsync

    fdatasync skips metadata such as mtime unless it's needed to read the data back. It's cheaper, and WALs use it.

    New file? fsync the directory

    The file's name lives in the directory. Atomic replace means: write tmp → fsync tmp → rename → fsync dir.

    "fsyncgate" (2018)

    On Linux, a failed fsync may drop the dirty pages, so retrying returns success with the data gone. PostgreSQL now panics instead of retrying.

    Lesson 13 · Network

    Socket buffers & backpressure

    Each TCP socket has a kernel send buffer and receive buffer. write() succeeds as soon as bytes fit in the send buffer, not when the peer receives them. When the receiver is slow, its buffer fills, TCP flow control (the receive window) stops the sender, the send buffer fills, and then write() blocks or returns EAGAIN. That chain is backpressure.

    Producer → send buffer → slow consumer
    0 / 64 units

    Never buffer unboundedly

    If your app catches EAGAIN and appends to an unbounded queue, you've thrown away backpressure and turned it into an OOM. Pause the producer instead: Node's 'drain', Netty's isWritable(), Reactive Streams request(n).

    Nagle & TCP_NODELAY

    Nagle's algorithm holds back small segments while earlier data is unacknowledged. Combined with delayed ACKs, that can add ~40 ms. Latency-sensitive apps set TCP_NODELAY (Go does this by default).

    Tuning

    SO_SNDBUF/SO_RCVBUF, net.ipv4.tcp_rmem. Buffer size should be about the bandwidth-delay product: 1 Gbps × 50 ms ≈ 6 MB.

    Hardware

    MMIO registers · polling burns CPU · interrupts free the CPU · DMA frees the CPU from copying · MSI-X gives per-queue interrupts

    syscall = mode switch · blocking = sleep on wait queue · page cache absorbs reads/writes · read-ahead · dirty writeback

    Throughput

    buffer small writes · batch syscalls · sendfile/splice · sequential > random · append-only logs
