An in-memory data structure server

Redis keeps its data in RAM and exposes rich structures (lists, sets, sorted sets and more) over a simple text protocol. Because there is no disk read on the hot path, a command returns in microseconds. Most of the time you see is the network.

Why one thread is fast enough

Each command runs to completion before the next starts, so INCR or a Lua script needs no locks. The cost is that one slow command (like KEYS * on millions of keys) blocks everyone.

Remember

  • Redis is a data structure server first and a cache second. The structure you pick decides which operations are cheap.
  • Data lives in RAM, so memory size is your capacity limit. Persistence is optional and covered in station 4.
  • A single command is atomic. Sequences of commands are not, unless you use MULTI/EXEC or a Lua script.

Remember

  • A TTL bounds how stale data can get. Deleting the key on write removes most staleness, but only if every writer does it.
  • Add a little random jitter to TTLs so a batch of keys does not all expire in the same second and stampede the database.
  • allkeys-lru drops the least recently used key, allkeys-lfu the least frequently used, noeviction returns an error on writes. Redis samples a few keys rather than tracking exact order.

Persistence: what survives a crash?

Redis can write snapshots (RDB), an append-only log of commands (AOF), or both. Add writes, take a snapshot, then crash the server and compare how much each mode keeps.

RDB snapshot

A forked child writes the whole dataset to dump.rdb at intervals (for example every 5 minutes if 100 keys changed). Compact and fast to load, but everything since the last snapshot is lost on a crash.

AOF log

Every write is appended to a file. appendfsync always syncs each command (safest, slowest). everysec loses up to about a second. no leaves flushing to the OS, which on Linux can mean around 30 seconds. The log is rewritten in the background to stay small.

Remember

  • A pure cache can run with no persistence. Anything you cannot rebuild should use AOF everysec at minimum, or RDB + AOF together.
  • Replication is not a backup. A bad FLUSHALL is replicated too, so keep snapshot files somewhere else.

Replication, failover and Cluster

Replicas copy the primary asynchronously. Sentinel promotes a replica when the primary dies. Redis Cluster goes further and splits the keyspace across several primaries.

Replication and failover

Cluster: 16384 hash slots

A key goes to slot CRC16(key) mod 16384, and each primary owns a range of slots. Only the part inside {braces} is hashed when present, which keeps related keys together.

More keys

Remember

  • Replication is asynchronous. A write acknowledged by the primary can be lost if the primary dies before replicas receive it (watch the “lost writes” count above).
  • Replicas scale reads and give you a failover target. Cluster scales writes and memory.
  • Multi-key commands in Cluster work only when all keys share a slot. Use hash tags like {user:1}:cart to arrange that.

Pub/Sub vs Streams

Both move messages between programs. Pub/Sub is fire and forget. Streams keep an append-only log with consumer groups, so work survives a consumer crash.

Streams + consumer group

Each entry goes to one consumer in the group. Unacknowledged entries stay pending and can be claimed.

Remember

  • Pub/Sub has no storage. Use it for live signals where missing one is fine (cache invalidation hints, chat presence).
  • Streams persist entries, track what each consumer has been given, and let another consumer take over stuck work. Use them for queues you cannot afford to drop.
