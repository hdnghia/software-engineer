Identity & access management, explained

ZITADEL decides who someone is and what they may do.

ZITADEL is an open-source identity platform. Your apps send users to it to log in, and it sends them back with a signed token that says who they are and which roles they hold. You stop writing login pages, password storage, MFA and SSO yourself.

Written in Go PostgreSQL Event sourced OIDC · OAuth 2.0 · SAML 2.0 Multi-tenant Cloud or self-hosted
What happens when a user clicks "Log in"?
  1. Your app redirects the browser to ZITADEL.
  2. ZITADEL shows the login page: password, passkey, Google, Microsoft…
  3. It checks MFA and policies for that user's organization.
  4. It sends the browser back to your app with a one-time code.
  5. Your app swaps the code for tokens and reads the user's roles.
The big picture

Think of ZITADEL as an office tower with a front desk

Every ZITADEL concept maps to something in a shared office building. Keep this picture in mind and the rest of the guide falls into place.

InstanceThe whole tower= one ZITADEL installation

Has its own domain (e.g. auth.acme.com), default settings and administrators.

OrganizationA company renting a floor= a tenant

Owns its own users, login policy, branding and domain. Floors are isolated from each other.

ProjectA product team's room= a group of apps + roles

Defines the roles (like admin, editor) that apps inside it understand.

ApplicationA door into the room= a client (web, mobile, API)

Has a client ID and redirect URLs. Each app talks OIDC, SAML or API auth.

UserA person with a badge= human or machine account

Belongs to exactly one organization. Can log in with password, passkey or an external IdP.

RoleWhat the badge opens= a permission label

Plain strings defined on a project. Your app checks them in the token.

AuthorizationBadge programmed for a room= user + project + roles

Also called a user grant. Gives one user some roles in one project.

Project grantLending your room to another company= B2B sharing

Lets another organization assign your project's roles to its own users.

Users

      
Two kinds of users: people and programs

    

    

      

        Human user
        
Someone who logs in through a browser

        
    
          
  • Has a username, email and profile.
    • 
          
  • Logs in with password, passkey, or an external IdP (Google, Entra ID, GitHub, any OIDC/SAML/LDAP).
    • 
          
  • Can add second factors: authenticator app (TOTP), SMS, email OTP, security key (U2F).
    • 
          
  • Can register themselves if the organization allows it.
    • 
        

      

      

        Machine user
        
A service account for backend jobs

        
    
          
  • No password and no login page.
    • 
          
  • Personal access token (PAT): a long-lived bearer token. Easiest to start with.
    • 
          
  • JWT profile: signs a JWT with a private key and exchanges it for a token. Most secure.
    • 
          
  • Client credentials: client ID and secret, standard OAuth.
    •

Grants

      
How roles reach users, including users in other companies

      
Acme owns the "Acme Tracker" project. Its customer Globex needs its own staff to use the tracker, and Globex's admin wants to decide who gets which role. A project grant makes this possible without Acme touching Globex's users.

    

    

      
    

    

      
Authorization (user grant)
"Give this user these roles in this project." Alice gets admin on Acme Tracker. It is the most common action you'll take in the Console.

      
Project grant
"Let this other organization hand out a subset of my roles." Globex can assign editor and viewer to its own people, but never admin.

    

  






  

    

      
What you get out of the box

      
Features, in plain words

    

    

      
Login UI
Hosted login pages
Ready-made login, registration, password reset and MFA screens. Or build your own with the Session API.

      
Passkeys · TOTP · OTP
Strong authentication
Passwordless login with passkeys (Face ID, Windows Hello, security keys) and second factors you can force per organization.

      
Identity providers
"Log in with…" buttons
Connect Google, Microsoft Entra ID, GitHub, GitLab, Apple, any generic OIDC, SAML or LDAP source.

      
Multi-tenancy
One system, many customers
Each organization has its own users, policies, branding and verified domains, fully isolated.

      
Branding
Your colors and logo
Customize logo, colors, fonts and texts per organization, so each customer sees their own brand on login.

      
Actions
Hook into events
Call your own webhook when something happens, for example to add custom claims to a token or sync a new user to a CRM.

      
Audit trail
Every change is recorded
Because ZITADEL stores events, you can see who changed what and when, for every object.

      
APIs
Everything is an API
The Console only uses public gRPC and REST (connectRPC) APIs, so anything you click can be automated.

      
Standards
OIDC, OAuth 2.0, SAML
Plugs into most frameworks and products, with token introspection, device flow, token exchange and SCIM provisioning.

    

  






  

    

      
Interactive · Under the hood

      
Event sourcing: ZITADEL remembers every change

      
Most systems overwrite a row when you change something. ZITADEL appends an event instead, and builds the current state by replaying events. That is why it has a complete audit trail for free. Try it on one user below.

    

    

      

        

        

      

      

        Projection: current state of user 2840…
        

        
The "projection" is a read model built from events. ZITADEL keeps many projections (users, orgs, tokens…) in PostgreSQL tables for fast queries.

      

    

  






  

    

      
Get started

      
From zero to a working login in eight steps

    

    
    
      
  1. Run ZITADEL
    Use ZITADEL Cloud, or self-host with Docker Compose next to PostgreSQL. The Console opens at http://localhost:8080/ui/console.
    2. 
      
  2. Create an organization
    One per customer or business unit. Small setups can use the default organization.
    3. 
      
  3. Create a project
    Name it after your product, for example "Acme Tracker".
    4. 
      
  4. Add roles to the project
    Plain keys such as admin, editor, viewer. Turn on "Assert roles on authentication" so they land in tokens.
    5. 
      
  5. Add an application
    Pick the type: Web, Native, User Agent (SPA) or API. Set the redirect URI, e.g. http://localhost:3000/callback. Copy the Client ID.
    6. 
      
  6. Create a user
    Or let people self-register, or connect Google or Entra ID as an identity provider.
    7. 
      
  7. Authorize the user
    Give them a role in your project. That's the authorization (user grant).
    8. 
      
  8. Wire up your app
    Point any OIDC library to your issuer. It discovers all endpoints from /.well-known/openid-configuration. Read roles from the token claim urn:zitadel:iam:org:project:roles.
    9.
