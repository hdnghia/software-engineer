Microservices, explained by running them

A shop splits into small services that each own their data. That solves some problems and creates new ones: how do you keep data consistent, survive a dead service, find the right instance, or rebuild state? Each lab below is a working miniature of one pattern. Click, break things, and watch what the pattern does about it.

Foundation

One big app, or many small ones?

A monolith is one deployable unit with one database. A microservice architecture splits it by business capability (orders, payments, stock), and each service owns a private database.

  • Decompose by business capability: services follow what the business does, not technical layers.
  • Database per service: nobody reads another service's tables. They ask through an API or events.
  • Strangler application: migrate gradually by moving one capability at a time out of the monolith.
Data management

Saga: a transaction without a shared database

Placing an order touches Order, Inventory and Payment, each with its own database. There is no single COMMIT across them. A saga runs a chain of local transactions. If one step fails, it runs compensating transactions to undo the earlier ones.

  • Orchestration: one coordinator tells each service what to do next.
  • Choreography: services publish events and react to each other's events. There is no central brain.
  • The system is briefly inconsistent while the saga runs (eventual consistency).

    Circuit breaker: stop calling what is already broken

    If Payment is down and Order keeps calling it, every call hangs, threads pile up, and Order goes down too. A circuit breaker counts failures. After a threshold it opens and fails instantly without calling the service. After a cool-down it lets one trial call through (half-open) to test recovery.

    • Threshold here: 3 consecutive failures. Cool-down: 6 seconds.
    • Pair it with a fallback (cached value, default, queue for later).

    Event sourcing & CQRS: store what happened

    Instead of overwriting a balance, event sourcing appends immutable facts: Deposited 50, Withdrawn 20. The current state is computed by replaying them. CQRS separates the write side (commands that validate and append events) from read models built from those events for fast queries.

    • Perfect audit trail, and you can rebuild state at any point in time.
    • Drag the slider to time travel. Try withdrawing more than the balance.
    • Costs: eventual consistency of read models and a mental shift.

      Edge & discovery

      API gateway, service registry, API composition

      Clients should not know where 12 services live. The API gateway is the single entry point: it routes requests, and for screens needing many services it uses API composition to call several and merge the answers.

      Instances come and go, so the gateway asks a service registry who is healthy (server-side discovery) and load balances across them.

      • Take instances down and call the same route again.
      • Take all instances of a service down to see a 503 and a partial dashboard.
